Case Study 03

ERW 강관 용접부 AI 검사 · 현장 피드백 서비스

노바투스 AI 교육 과정(2026.05 –)의 팀 프로젝트입니다. 전기저항용접(ERW) 강관의 용접부 단면 사진 한 장을 받아, 외부 CV 측정 API로 치수를 재고, 사진 판정 모델로 합격/불합격을 가리고, 검사기준 매뉴얼을 근거로 원인과 조치 문장까지 만들어 주는 FastAPI 백엔드를 혼자 설계 · 구현했습니다.

기간 · 소속
2026.10 · 노바투스 AI 교육
역할
백엔드 단독 (API · 파이프라인 · 문서)
팀
팀 프로젝트 · 프론트 · 모델 담당과 협업
스택
FastAPI · Gemini · scikit-learn

문제

현장 작업자가 바로 따라 할 수 있는 조치 문장이 필요했지만, LLM이 매뉴얼에 없는 설비 조작을 지어내면 안 됐고, 처리에 20초 넘게 걸렸습니다.

내가 한 일

측정 → 판정 → 피드백 3단계 파이프라인, 단계별 SSE 스트리밍, 표 조회형 RAG, 조치 어휘 enum 검증, 유사 사례 검색, 단계별 대체 경로를 만들었습니다.

결과

조치의 내용과 순서는 규칙이 정하고 LLM은 문장만 쓰는 구조. 외부 API · 모델 · LLM 어느 것이 실패해도 끝까지 응답합니다.

처리 흐름 SSE 스트리밍 표 조회형 RAG LLM 출력 통제 유사 사례 검색 판정 모델 연동 장애 대응 기술 스택

02단계별 SSE 스트리밍

CV 측정만 20초, LLM 생성까지 하면 30초 넘게 걸립니다. 결과를 한 번에 주면 화면이 그동안 멈춰 있게 되어, 단계가 끝날 때마다 이벤트로 흘려보내게 했습니다.

이벤트시점 · 내용
stage각 단계 시작 — 화면 상단 진행 단계 갱신
cvCV 측정 완료 — 측정값 · 측정 불가 사유
panel측정 도판 이미지를 1장씩(최대 9장) 전송 — 4MB를 한 번에 보내지 않음

  • 브라우저 EventSource는 GET만 지원해 이미지 업로드가 안 되므로, POST + fetch · ReadableStream으로 받는 방식을 정해 문서에 남겼습니다.
  • 근거 데이터(references)를 LLM 생성보다 먼저 보내, LLM이 느리거나 실패해도 작업자는 기준 이탈 항목과 조치를 먼저 볼 수 있습니다.

03왜 일반 RAG가 아니라 표 조회형 RAG인가

문서를 잘라 임베딩하고 벡터 DB에서 비슷한 문단을 찾는 일반적인 RAG 대신, 측정값을 검사기준 표와 직접 대조하는 방식을 택했습니다.

측정값 → 관리 한계와 비교 → 이탈 항목(NG_ID) → 원인 · 조치 조회 → Gemini가 문장 작성
판단 근거내용
입력이 숫자입력은 문장이 아니라 측정값입니다. 기준 초과 여부로 이탈 항목이 정확히 정해져 의미 유사 검색이 필요 없습니다.
오검색 위험"내면 과다 → 누르기 / 외면 과다 → 들기"처럼 비슷한 문장이 많아, 조각내 검색하면 반대 조치가 섞일 수 있습니다.
설비 조작 지시틀린 조치는 허용되지 않습니다. 표 조회는 결과가 결정적이고 "어떤 값이 어떤 기준을 넘어서 나온 조치인지" 근거를 댈 수 있습니다.
분량매뉴얼은 5쪽, 표 약 170행이라 임베딩 모델 · 벡터 DB가 과합니다.

매뉴얼이 크게 늘거나 자유 질문 챗봇을 붙이게 되면 일반 RAG를 다시 검토하도록 문서에 조건을 남겼습니다.

04LLM 출력 통제: 조치는 규칙이, 문장은 LLM이

  • 검사기준 엑셀의 조치 시트를 enum으로 고정했습니다 — 대상 14종, 조작 13종, 세부 조건 20종, 실행 조건 5종, 핀패스 번호 3종.
  • 서버가 시작할 때 시트 전체를 검증합니다. 매뉴얼에 새 값이 생기면 행 번호와 함께 오류를 내서 바로 알 수 있습니다.
  • 검색된 조치마다 id(A1, A2 …)를 붙여 Gemini에 넘기고, Gemini는 id별 문장만 씁니다. 모르는 id · 중복 id는 버리고 빠진 조치는 표준 문구로 채웁니다 — 매뉴얼에 없는 조치는 응답에 들어올 수 없습니다.
  • 조치 순서는 규칙이 정하고(재측정은 항상 마지막), 각도 분기는 실제 측정값에 해당하는 쪽 조치만 남깁니다.
  • LLM 응답에 내부 용어('모델1', '사례 은행', 사례 번호)가 섞이면 서버가 지우고, 현장에서 바로 이해하는 말('사진 판정', '과거 검사 기록')로 쓰도록 프롬프트를 다듬었습니다.

05유사 사례 검색

과거 검사 기록 251건 가운데 측정값이 가장 가까운 사례를 찾아 프롬프트와 화면에 함께 씁니다.

  • 측정값을 z-score로 표준화하고, 도메인 가중치를 둔 가중 유클리드 거리로 가까운 5건을 고릅니다. 학습이 필요 없는 방식이라 결과를 설명하기 쉽습니다.
  • 사례 은행의 열 이름을 CV API 코드와 맞춰 변환 없이 비교하고, 같은 사진 6장으로 은행 값과 일치하는지(거리 0으로 1위) 확인했습니다.
  • 사진 판정이 불합격일 때만 가장 가까운 불합격 사례 1건을 보여 줍니다. 은행의 81%가 불합격이라 "가까운 5건 중 불합격 4건" 같은 분포가 합격 판정과 엇갈려 보이는 혼란을 막기 위해서입니다.
  • 차이가 큰 특징 4개를 함께 보내 화면이 "어디가 얼마나 다른지" 보여 줄 수 있게 했습니다.

06사진 판정 모델 연동

  • 전달받은 사진 판정 모델(OpenCV로 용접선 옆 4곳 추출 → CNN 5개로 각도 측정 → RandomForest 판정)을 서비스에 붙이고, 학습 · 예측 로직을 저장소에 정리했습니다.
  • 이후 실무자 판정 데이터(138건)로 학습한 모델로 교체했습니다.
  • 모델의 합격 기준값(OK 확률 0.30)을 화면의 0.5 기준과 맞추는 불량 점수로 변환하고, 이것이 보정된 확률이 아님을 응답 명세에 분명히 적었습니다.

07장애 대응: 어느 단계가 실패해도 끝까지 응답

실패대응
CV API 미응답로컬 대체값으로 이어감 (features._source로 구분)
모델 파일 없음 · 사진 처리 실패UNKNOWN 판정과 사유(note)로 이어감
Gemini 장애 · 과부하매뉴얼 원문으로 같은 구조의 피드백 생성
Gemini 모델 사용 불가사용 가능한 모델을 순서대로 시도해 자동 선택
사례 검색 실패빈 사례로 흐름 계속

대체값으로도 처리할 수 없는 예외일 때만 스트림에 error 이벤트를 보내고, 키가 하나도 설정되지 않은 환경에서도 모든 엔드포인트가 정상 응답합니다.
